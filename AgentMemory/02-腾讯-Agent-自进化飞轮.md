# 第二篇：Agent 自进化飞轮

来源：一篇讲透 Agent 自进化飞轮怎么搭：评测→记忆→落地→控制

## 一句话总结

Agent 自进化不是让模型自动“变聪明”，而是搭建一个可验证、可回滚、能持续回流的工程闭环：评测发现问题，记忆保存经验，工程流程生成并验证修改，人机协作控制方向和风险。

## 1. 这篇文章和第一篇是什么关系

第一篇主要回答：

> Agent 的记忆系统应该如何分层、读取和写入？

第二篇继续回答：

> 记忆中的经验如何转化为 Skill、Prompt 或工具配置的改进，并安全地影响下一轮任务？

因此，第二篇不是单纯讲“记忆”，而是把记忆放进更大的自进化系统中。

## 2. 先对齐：到底什么在进化

文章把“自进化”分为三层：

| 层级 | 改变的对象 | 特点 |
|---|---|---|
| Artifacts 迭代 | 本次任务的输出 | 多改几版、让本次结果更好；任务结束后 Agent 本身不变 |
| Harness 自改进 | Memory、Skill、Prompt、工具配置、Workflow | 修改可以持久化，后续任务继续受益 |
| Model 进化 | 模型参数 | 持久性最强，但成本和风险最高 |

文章的主战场是 Harness 层。

例如 Agent 经常把日期格式转换错：

- Artifacts：本次多试几次，最后改对；
- Harness：沉淀一条 Skill，规定先识别源格式再转换；
- Model：用大量样本重新训练模型。

对于大多数团队，先把经验写入 Skill、Prompt、记忆和工具配置，通常比直接训练模型更快、更可控，也更容易回滚。

## 3. 四个齿轮

```text
评测：发现哪里有问题
  ↓
记忆：保存可复用的经验和教训
  ↓
落地：生成候选修改并验证
  ↓
控制：人工审核、灰度、回滚、方向审计
  ↓
线上新数据回流到下一轮评测
```

四个环节必须有数据通路：

1. 评测 → 记忆：好的经验和反例被保存；
2. 评测 → 落地：失败模式转化为修复方向；
3. 落地 → 控制 → 生效：候选修改通过门控、审核和灰度；
4. 生效 → 下一轮评测：上线后的真实表现继续产生新信号。

只做其中一个组件，不会自然产生“飞轮”。真正重要的是箭头是否接通。

## 4. 第一齿：评测不是打分，而是信号源

自进化场景下，评测有三种职责：

- 方向指引：告诉系统下一步该改哪里；
- 质量门控：判断修改后有没有退化；
- 经验筛选：判断本次执行是否值得写入长期记忆。

这比传统的“上线前测一下”更重要。传统评测打错分，可能只是放过一个质量不高的版本；自进化评测打错分，可能让 Agent 把错误经验长期写入记忆和 Skill。

### 4.1 评测的核心难题

文章集中讨论了七个问题：

1. 评估器有偏差，例如偏好更长的答案；
2. 只看最终答案，看不到错误的推理或工具调用；
3. 粗粒度只能知道“错了”，细粒度又非常昂贵；
4. 写作、规划等开放式任务缺少绝对标准；
5. 评测集长期不更新，出现评测集漂移；
6. 新版本可能只是多花了 Token，并不是真正进化；
7. 每次都跑全量评测，成本会限制迭代速度。

最值得记住的是第一个：

> 错误的正反馈，比没有反馈更危险。

### 4.2 建设一套可信的评测体系

建议采用分层组合：

```text
规则校验
  ↓
LLM Judge + 对照实验
  ↓
人工抽样 + 元评测集
```

- 能用规则判断的，就不要调用 LLM，例如格式、字段、测试、SQL 结果和响应时间；
- LLM Judge 要和生成模型分离，结构化输出，按维度独立评分；
- 评估模型尽量固定 temperature，保证结果可复现；
- 定期人工抽样，检查 LLM Judge 和人的判断是否一致；
- 维护少量“绝对正确”和“绝对错误”的元评测样本，专门检查评估器本身。

### 4.3 评测集不能只有一份

文章借用了 train / val / test 的职责分离：

| 数据集 | 用途 | 是否用于生成修复方案 |
|---|---|---|
| train | 诊断失败模式 | 可以暴露给诊断流程 |
| val | 筛选候选版本 | 不应暴露给生成修复的模型 |
| test | 上线前最终验证 | 保持独立 |

否则 Agent 会反复针对同一批题目优化，最后只是“刷高分”，并不代表对新问题有效。

### 4.4 评测终点是诊断归因

“得了 60 分”不能直接指导修复。需要继续判断：

- 是 Prompt 不清楚？
- 是 Skill 逻辑有问题？
- 是工具 API 参数错误？
- 是服务端没有返回数据？
- 是数据本身有问题？

不同根因应进入不同链路：

| 失败类型 | 后续动作 |
|---|---|
| 系统性错误 | 修改 Skill / Prompt，并写入 Playbook |
| 偶发错误 | 记为教训或反例，供后续召回 |
| 能力缺失 | 补充工具、知识或外部研究 |
| 回归问题 | 立即回滚，并由人判断后续处理 |

一个很实用的排障原则是：连续多轮失败率不下降时，先检查工具实现、API 参数和真实返回值，不要只在 Prompt 层反复试错。

### 4.5 Skill 不能“看起来有用”就算成功

一个 Skill 至少要经过四层验证：

1. 有 Skill 和无 Skill 的对照实验，确认确实产生增量；
2. 任务难度要合适，太简单看不出 Skill 的价值；
3. 追踪执行轨迹，确认 Agent 真的调用了 Skill 中的步骤；
4. 检查路径是否正确，不能只看最终答案碰巧正确。

## 5. 第二齿：记忆的核心是治理

文章对第一篇进行了进一步抽象：

> 向量库只是存储组件，不等于记忆系统。

记忆系统要治理三个环节：

- 写入：什么值得记住，什么只是噪声；
- 存储：如何版本化、更新、遗忘和解决冲突；
- 读取：如何精准召回，同时不挤爆上下文窗口。

### 5.1 写入：策展，而不是全存

文章建议：

- 有明确正向信号时再写入长期记忆，例如用户确认、评测通过、任务成功；
- 失败也可以保存，但要标记为“反例”或“陷阱”，写清楚为什么失败；
- 经验通过多次验证逐步晋升为正式 Skill；
- 坏经验的淘汰速度应快于好经验的强化速度。

### 5.2 存储：分层 + 生命周期

文章给出了一种 L0-L3 的分层思路：

```text
L3：用户画像 / 高密度摘要
L2：场景块
L1：原子事实
L0：原始对话和证据
```

默认只加载高层、轻量的信息；遇到不确定性时，再通过节点标识回溯到底层证据。

每条记忆还应具备：

- 版本号；
- 来源会话和触发原因；
- 更新时间和使用情况；
- 过期、衰减或淘汰策略；
- 冲突处理和并发控制。

### 5.3 读取：渐进披露 + 严格预算

不要一次性把所有历史记忆塞入 Prompt，而是：

1. 默认注入最小背景；
2. 根据当前任务召回中层事实和场景；
3. 只有需要证据时才钻取原始对话。

文章给出的示例预算是：Skill、Facts、Profile 分别设置上限，单条记忆限制长度，整体限制条数，并根据任务复杂度动态调整。这些数字是实现参考，不是通用标准。

## 6. 第三齿：从“知道问题”到“安全修复”

文章强调：自动化不等于全自动。

从发现问题到修改生效，至少包括八步：

```text
诊断归因
  ↓
汇聚本轮评测、历史 Playbook、外部知识
  ↓
生成多个候选方案
  ↓
隔离环境独立评测
  ↓
语法/回归/显著性/一致性门控
  ↓
人工确认
  ↓
小流量灰度
  ↓
监控回流 + 经验沉淀
```

### 6.1 为什么要生成候选，而不是直接改

候选方案应采用 Diff 模式，只输出需要修改的部分，而不是让 LLM 全文重写 Skill 或 Prompt。

Diff 模式的好处：

- 修改范围清楚，便于 Review；
- 不容易覆盖无关的正确逻辑；
- 可以按 patch 精准回滚；
- 更容易把修改和评测结果关联起来。

多个候选必须在相互隔离的环境中评测，否则候选之间可能互相污染测试结果。

### 6.2 门控、灰度和回流

评测通过不等于可以全量上线。文章建议：

- 先做语法检查；
- 再做回归检测；
- 检查提升是否具有统计意义；
- 检查是否符合历史 Playbook；
- 最后由人做语义和业务确认；
- 小流量灰度，持续观察成功率、Token、延迟和用户反馈；
- 出现严重退化时自动回滚；
- 将灰度期新失败样本送入下一轮评测。

这里很像 Agent 版本的 CI/CD：被持续修改的对象不再只是代码，还包括 Prompt、Skill 和记忆。

### 6.3 Dreaming：异步发现慢变量

同步评测适合发现“这一次任务哪里错了”，但不容易发现跨会话的系统性问题。

Dreaming 可以在空闲时批量查看历史轨迹，寻找：

- 多次出现的失败模式；
- 成功但低效的执行路径；
- 反复依赖外部搜索的知识缺口。

它只负责发现和提出建议，最终是否修改仍需进入正式评测、门控和人工确认流程。

## 7. 第四齿：控制不是拖慢效率，而是保证方向

完全自动进化会有“对齐漂移”：每次修改看起来都合理，但连续很多次后，Agent 可能逐渐偏离最初意图。

例如目标是“准确且简洁”，评测器却偏好内容更长。每一轮分数都可能上升，但 Agent 最后变得越来越啰嗦。

文章建议采用分级自治：

- 稳定、低风险领域可以提高自动化程度；
- 新领域、高风险操作保持人工参与；
- 长期稳定后逐步放权；
- 出现严重回归时自动降级。

五个不能完全交给 Agent 的节点：

1. 规则级记忆写入前；
2. Prompt / Skill 的最终确认，尤其是安全、拒答和权限逻辑；
3. 评测出现回归时的处理决策；
4. 新领域冷启动时的第一批评测集、Skill 和安全边界；
5. Agent 自身权限边界的设定和调整。

### 7.1 防止审核疲劳

如果所有修改都弹给人审核，人最终可能会机械点击通过。

更合理的做法是：

- 先用自动门控过滤低质量候选；
- 批量异步审核，而不是逐条打断；
- 展示评测数据、影响范围和典型样例；
- 根据长期表现渐进放权，并在回归时自动降级。

## 8. 从零落地路线

文章给出的路线可以理解为：

| 阶段 | 目标 | 主要动作 |
|---|---|---|
| Phase 1 | 跑通最小闭环 | 设计评测集，使用 Markdown 记忆，人工完整跑一轮 |
| Phase 2 | 半自动化 | Skill 生成、CI 评测门禁、版本管理、train/val/test 分离 |
| Phase 3 | 飞轮持续运转 | 灰度、回流、Dreaming、渐进放权 |
| Phase 4 | 元进化 | Auto-Research、进化策略优化、多 Agent 协同 |

最重要的建议是：先手动跑通第一圈。

一个能人工转起来的粗糙闭环，比一个自动化程度很高但没有验证过的架构蓝图更有价值。

## 9. 我的理解：这篇最值得带走的四点

### 9.1 Memory 和 Playbook 不是一类东西

- 通用 Agent Memory：帮助 Agent 更好地完成任务；
- Evolution Playbook：帮助系统更好地修改 Agent。

两者都可以使用检索和版本管理，但服务对象不同，最好不要混成一个池子。

### 9.2 评测结果必须能触发动作

如果评测只生成周报，系统不会进化。至少要把结果映射到：

```text
失败模式 → 修复类型 → 候选变更 → 验证集 → 灰度 → 回流
```

### 9.3 自进化系统首先是一个安全系统

写入门控、版本化、Diff、隔离评测、自动回滚、人工边界，这些机制不是附属功能，而是防止错误被持续放大的基础设施。

### 9.4 “更高分”不一定代表真正进化

必须同时检查：

- 是否在相同 Token 预算下提升；
- 是否只对旧评测集有效；
- 是否牺牲了延迟、稳定性或简洁性；
- 是否真的使用了新增 Skill；
- 是否发生了长期方向漂移。

## 10. 需要批判性阅读的地方

文章提到的“迭代次数减少”“Token 消耗降低”“解决率提升”等数字，应理解为作者引用的案例或实践观察，不能直接当作所有 Agent 的普遍效果。

文章的价值主要在于提出一套完整的工程框架；真正落地时，还需要用自己的业务指标、评测集和线上数据验证。

## 课后练习

1. “用户说上次方案不可行，以后遇到这个 API 不要使用默认 timeout”应该写成普通记忆、反例，还是规则级记忆？为什么？
2. 如果一个新 Skill 让成功率从 80% 提升到 85%，但 Token 消耗增加 3 倍，你会直接判定它进化了吗？
3. 为什么“评测 → 落地”之间必须有诊断归因，而不能让 LLM 直接根据分数重写 Skill？
4. 为你自己的 Agent 设计一个最小闭环：10 条评测 case、1 个 Markdown 记忆文件、1 次人工修改、1 次回归验证。

## 本篇最终结论

> 自进化的核心不是让 Agent 自己修改自己，而是让每一次执行都产生可验证的信号，让每一条经验都经过治理，让每一次修改都能灰度、回滚，并在上线后回流到下一轮评测。
