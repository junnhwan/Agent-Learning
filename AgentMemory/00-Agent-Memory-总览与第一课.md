# Agent Memory 学习笔记：总览与第一课

> 阅读材料：`AgentMemory/` 目录下 7 篇文章，共 151 页。
> 本笔记区分三类内容：`原文观点`、`作者自报实验`、`我的归纳`。

## 一、先给结论

这些文章不是 7 个互不相关的方案，而是在讨论同一条链路：

```text
任务轨迹
  -> 候选记忆提取
  -> 验证、归类、绑定作用域
  -> 分层存储与版本治理
  -> 按任务检索和 Token Budget 装配
  -> Agent 执行
  -> 结果评测与反馈
  -> 记忆更新、降权、遗忘或升级为 Skill
```

最重要的判断是：

> Agent Memory 不是“把聊天记录存进向量数据库”，而是一个带有写入策略、检索策略、生命周期、权限、证据链和评测闭环的信息治理系统。

## 三、统一概念：不要把几个词混在一起

### 1. Context：当前推理要直接读的上下文

例如本轮用户消息、最近几轮对话、当前工具结果。它直接进入模型输入，受 Token 窗口限制。

### 2. State：任务运行状态

例如当前做到第几步、已经尝试过什么、哪个子任务完成、哪个文件被修改。它关注“任务现在进行到哪里”。

### 3. Memory：跨轮次或跨会话可复用的信息

例如用户偏好、稳定事实、历史决策、失败教训、已验证的操作方法。它关注“以后还能不能减少重复劳动”。

### 4. Knowledge：相对稳定的外部事实或组织资料

例如 Wiki、架构规范、Runbook、业务规则。它未必来自某次 Agent 对话，也不一定是个人记忆。

### 5. Skill：可重复执行的方法

它不仅是“知道某件事”，还包含触发条件、步骤、工具调用、边界和验证方式。Skill 可以看成经过验证、可执行化的经验。

一个简单判断：

```text
当前马上要读       -> Context
任务中断后要接着做  -> State
下次类似任务还要用  -> Memory
团队长期事实        -> Knowledge
可以按步骤复用      -> Skill
```

## 四、记忆的两个正交维度

得物文章特别提醒：四层记忆和 MemOS 的 `text_mem`、`pref_mem`、`skill_mem`、`tool_mem` 不是同一套分类。

- 生命周期/作用域维度：Working、Session、User、Agent。
- 内容形态维度：事实、偏好、技能、工具经验、任务背景等。

因此不能简单画成“每一层只放一种内容”。例如：

- User Memory 可以保存用户偏好，也可以保存稳定事实；
- Agent Memory 可以保存某个 Agent 的任务经验和协作约定；
- Session Memory 可以在会话结束后提炼出 User 或 Agent Memory；
- 同一条记忆还应有来源、时间、版本、权限和验证状态。

## 五、第一课：为什么“全量保存 + Top-K 召回”不够

### 1. 写入问题

一次 Agent 执行会产生大量消息：用户输入、模型回复、工具返回、搜索结果、中间推理和失败尝试。绝大多数内容不值得长期保存。

要问的不是“能不能存”，而是：

- 这条信息未来是否可复用？
- 它是事实、偏好、任务状态、失败反例，还是临时噪声？
- 它是否已经被验证？
- 它适用于哪个用户、团队、Agent、项目、分支和版本？

### 2. 读取问题

向量相似不等于任务相关，也不等于当前可用。两个记忆可能语义相近，但适用分支、路径、时间或权限不同。

所以成熟的读取顺序应接近：

```text
身份/租户/ACL 过滤
  -> 固定绑定资产
  -> 语义、关键词、精确匹配召回
  -> 融合排序与冲突检查
  -> 按版本和 Token Budget 装配
  -> 必要时回溯原始证据
```

### 3. 治理问题

记忆不是写入后永远有效。至少需要支持：

- 新增、更新、合并、分裂；
- 版本、来源、最后验证时间；
- 冲突检测与人工仲裁；
- 过期、降权、撤回、删除；
- 使用记录和可追溯证据；
- 负反馈能影响后续召回。

## 六、七篇文章合在一起后的生产级架构

```text
短期层：当前 Session / Working Context
        - 最近消息、工具结果、任务状态
        - 滑动窗口、摘要、卸载、上下文隔离

长期层：User / Agent / Team Memory
        - 事实、偏好、经验、失败反例、Skill
        - 分层、版本、作用域、ACL、生命周期

知识层：Wiki / CodeGraph / Runbook
        - 稳定事实、代码关系、确定性验证入口

控制层：评测、门控、灰度、回滚、人工确认
        - 判断记忆是否有用，也判断修改是否安全
```

## 七、重要实验数字：只按原文范围理解

这些数字是文章作者在特定模型、数据集或内部环境中的报告，不能直接外推成行业普遍结论：

- 得物：1,540 个问题、10 个测试用户，报告综合得分 74.33%；这是选型参考，不代表生产 SLA。
- TencentDB 团队实践：内部分析从 2,600 个 Session 切分出 5,081 个 Task；强关系只保留 231 条，其他关系降为 Shadow；相关 SWE-bench 测试报告完成率从 60% 到 80%。文章同时明确提示结果受 Case、模型、抽取、检索和重复次数影响。
- 腾讯自进化飞轮：建议先做 50-100 条 Case 的人工最小闭环，再逐步加入 CI、版本、灰度、回流和异步 Dreaming。
- 评测综述：MemoryAgentBench 的重点是准确检索、测试时学习、长程理解、冲突解决；LONGMEMEVAL 强调时间感知；MemBench 同时看准确率、召回率、容量和效率。

## 八、第一课练习

给下面这句话分类：

> “上次部署失败是因为测试环境读取了 `conf/prod/`，以后修改部署配置前必须先确认当前分支和运行环境。”

建议拆成两条，而不是存成一段聊天记录：

1. 事实/经验：上次失败的根因是什么，来源是哪次任务，适用哪个仓库和分支。
2. Skill/反例：修改部署配置前要检查分支、环境和配置路径，并用什么测试验证。

然后回答三个问题：

1. 这条内容应该进入 User、Agent 还是 Team 作用域？
2. 没有验证结果时，能否直接作为强规则注入？
3. 如果半年后目录结构变化，系统如何发现它可能过期？

我的初步答案：通常应进入项目/团队作用域；未经验证只能作为低置信背景或候选经验；必须绑定版本、最后验证时间和失败反馈，不能只靠向量相似度解决过期问题。
