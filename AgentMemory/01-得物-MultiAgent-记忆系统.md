# 第一篇：企业级 MultiAgent 的记忆系统

来源：企业级 MultiAgent 的记忆系统：短期上下文与四层记忆架构实现｜得物技术

## 一句话总结

得物这篇文章的核心不是“接入 MemOS”，而是把记忆嵌入 Agent 的完整执行链路：请求前并行加载短期和长期信息，会话结束后异步筛选、去重、处理冲突并沉淀到不同作用域。

## 1. 它在解决什么问题

MultiAgent 请求可能同时经过模型、MCP/A2A 工具、RAG、Workflow 和 Sandbox。只靠当前 Prompt 会产生三个问题：

1. 当前会话历史不够，无法稳定完成指代消解和任务延续。
2. 换会话或换 Agent 后，用户偏好和稳定事实无法复用。
3. 新消息无法和历史上下文建立关联，Agent 容易重新探索。

因此，记忆模块不是一个独立的“外挂数据库”，而是 Agent 执行链路的一部分。

## 2. 四层记忆模型

| 层级 | 保存什么 | 生命周期/作用域 | 例子 |
|---|---|---|---|
| Working Memory | 当前一步推理所需的信息 | 当前推理步骤 | 当前工具结果、临时中间状态 |
| Session Memory | 当前会话的消息历史 | 当前 Session | 用户消息、模型回复、工具调用和结果 |
| User Memory | 跨 Agent 共享的用户偏好和稳定事实 | 用户维度 | 用户喜欢简洁回答、长期偏好 |
| Agent Memory | 某个 Agent 的任务经验和协作约定 | Agent 维度 | 某 Agent 处理某类任务的经验 |

会话结束后，新增消息从 Session 层经过判断和去重，沉淀到 User 或 Agent 层。

一个关键辨析：四层是“生命周期和作用域”的分类；MemOS 的 `text_mem`、`pref_mem`、`skill_mem`、`tool_mem` 是“内容形态”的分类。两者不是一一对应关系。

## 3. 一次请求如何读取记忆

```text
AgentExecutor#execute
        |
        +-- 短期链路：ConversationMemory
        |       Redis 优先 -> MySQL 回退 -> Token 窗口裁剪
        |
        +-- 长期链路：queryMemory
                MemoryRpcServiceImpl 按配置选择 MemOS / Mem0 / MySQL
                -> user_profile + agent_{agentId}
                -> 相关性、敏感内容、长度过滤
                -> Token Budget 分配

两条 Future 在 memoryLoadExecutor 中并行执行
        |
        +-- join 汇合
        -> 写入 AgentContext
        -> 和短期消息一起参与模型调用
```

### 3.1 并行加载的真实含义

短期记忆和长期记忆提交到专用线程池并行执行，目的是重叠 I/O 和远程调用时间。

但这不代表长期检索会先读取短期历史再增强查询。文章明确指出，当前长期查询以本轮 `originalMessage` 为主查询词，短期历史和长期记忆互不等待。因此这里的并行主要优化延迟，不自动提升查询语义质量。

### 3.2 Provider 和降级边界

- 未配置长期记忆、Agent 不存在或读取配置异常时，路由到 MySQL。
- 明确配置为 MemOS 或 Mem0 时，才进入对应 Provider。
- `openLongMemory` 关闭时，长期结果为空。
- 未绑定模型时，不发起长期检索。
- 长期查询异常时记录日志并返回空结果，主对话继续。
- MemOS 查询异常当前不会自动切换到 MySQL。

最后两点体现了“增强能力失败不阻断主链路”的设计，但也意味着长期记忆失效可能表现为 Agent 突然变得不连续，需要额外监控。

## 4. 短期记忆如何实现

### 4.1 存储

- MySQL 是持久化底座。
- Redis 是热点缓存。
- 写入时先落 MySQL，再写 Redis。
- Redis 使用 List，最新消息放在表头；超过 200 条后从尾部淘汰最旧消息。
- Redis 写失败不会回滚已经完成的 MySQL 写入；读取时可以回源 MySQL。

这是一种“数据库保证持久性、缓存保证读取速度”的典型组合。

### 4.2 Token 窗口

读取历史后，从最新消息向前累加 Token：

1. 如果没有超出窗口，保留完整历史。
2. 如果超出窗口，只保留最近仍能放入窗口的消息。
3. 预留摘要空间；有摘要时，把摘要放到保留窗口前面。
4. 通过消息类型和交替关系校验，避免留下不完整的对话结构。

文章还提到，会话结束时只有当未被摘要覆盖的消息达到 20 条，才触发摘要生成；摘要预算约 2,000 tokens，并缓存 1 小时，避免每轮都调用摘要模型。

## 5. 长期记忆如何读取

当前 MemOS 查询同时覆盖两个 Cube：

```text
readableCubeIds = ["user_profile", "agent_" + agentId]
```

主要处理包括：

- 开启 preference 检索，偏好补充最多 6 条；
- 低于 `score < 0.3` 的结果过滤掉；
- 单条结果最多保留 1,000 个字符；
- 按分数降序排列；
- 长期记忆总预算默认 4,000 tokens；
- User Profile 最多占 60%，如果没有用满，剩余预算给 Agent Memory；
- 采用按行截断，尽量不拆散一条记忆。

这里体现的是“按作用域分组后再分配预算”，而不是把所有结果放进一个 Top-K 列表。

## 6. 长期记忆如何写入

```text
会话结束
  -> Redis 会话锁
  -> 消息 hash 去重
  -> 标记本次新增消息 [[NEW]]
  -> LLM 判断是否值得写入、属于哪个 scope、重要性是多少
  -> 本地相似度预去重
  -> 冲突检测与解决
  -> 先写新记忆
  -> 再尽力删除冲突旧记忆
  -> 检查是否生成会话摘要
```

### 6.1 幂等和去重

- 同一会话使用 Redis 分布式锁，避免并发处理同一个会话结束事件。
- 用 `MD5(role:content)` 作为消息标识。
- 已处理 hash 的 TTL 为 7 天，锁的有效期约 10 分钟。
- LLM 先在完整上下文中标记新增消息，再提取候选记忆。
- LLM 异常或返回为空时，降级到只基于新增消息的规则判断。
- 单条长期记忆截断到 200 字符。
- 本地预去重依次考虑 exact、contains、字符级 Jaccard 和短文本 Levenshtein。

注意：hash 写入失败或 Redis 读取失败时，系统可能把整段会话再次当成新增内容处理；这是 best-effort 幂等，不是严格事务。

### 6.2 冲突和先写后删

跨历史记忆的冲突交给冲突服务处理。遇到冲突时，系统可能：

- 保留新记忆；
- 跳过新记忆；
- 保留新记忆，并把旧记忆标记为待失效。

删除策略是“先写新记忆，后删旧记忆”。这样可以降低数据丢失风险，但不是事务级一致性：外部 MemOS 删除失败时，新记忆已经存在，旧记忆可能暂时仍会被召回。

文章还明确指出，外部服务失败后当前没有自动回放机制，因此生产环境要同时观察重复写入和处理中断。

## 7. 这篇文章真正值得学习的四个设计点

### 设计点一：作用域比相似度更重要

User Memory 和 Agent Memory 不是“多存一个字段”，而是决定谁能看到、谁应该复用。相似度只能回答“像不像”，不能回答“属于谁、适不适用”。

### 设计点二：读写时机分离

请求前读取要快，所以并行、缓存、降级；会话后写入可以慢，所以异步执行 LLM 判断、去重和冲突处理。这是实时体验和长期质量之间的折中。

### 设计点三：长期记忆必须有预算

召回越多不一定越好。User Profile 和 Agent Memory 需要竞争有限的上下文空间，按作用域和 Token Budget 控制，才能避免记忆挤压当前任务。

### 设计点四：写入不是简单 append

真正的长期记忆写入至少包含：新增判断、去重、冲突、作用域、重要性、失效旧记忆和摘要。向量库只是其中的存储/检索基础设施。

## 8. 读文章时要保持警惕的地方

下面是我的工程判断，不是文章原文结论：

1. 长期检索失败返回空结果，主链路虽不中断，但可能造成静默降级；需要记录命中率、空结果率和 Provider 错误率。
2. 长期查询主要使用本轮原始消息，遇到“这个/上面那个/继续刚才方案”时，可能缺少短期上下文增强。
3. 固定 4,000-token 总预算和 User Profile 60% 上限简单可控，但未必适合所有 Agent 或任务类型。
4. LLM 判断、相似度去重和冲突处理都可能出错，应该保留来源、版本、验证状态和可回溯证据。
5. “先写后删”偏向可用性和防丢数据，但需要后台清理、重试和一致性巡检补足。

文章中的 MemOS 评测分数是特定数据、模型和配置下的选型参考，不等于线上 SLA；文章最后也承认还需要补充生产流量下的延迟、失败率和补偿机制观测。

## 9. 本篇练习

请判断下面三条信息应该落在哪一层：

1. “用户希望以后所有回答都简洁。”
2. “当前订单排查已经完成支付查询，下一步检查库存。”
3. “这个 Agent 处理 Redis 超时问题时，通常先检查连接池，再检查重试配置。”

参考答案：

1. User Memory；跨 Agent、跨会话都可能复用。
2. Session/Working State；只服务当前任务，不应直接变成长期规则。
3. Agent Memory 或 Skill 候选；它与某个 Agent 的任务经验有关，经过验证后才适合升级为稳定 Skill。

## 10. 本篇应记住的一句话

> 得物的重点不是“把记忆接上”，而是把记忆变成请求前可加载、会话后可沉淀、作用域清楚、预算可控、失败可降级的 Agent 基础链路。
